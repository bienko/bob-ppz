    MODULE 1 | ANALYZE

    UNDERSTANDING THE CICS BANKING SAMPLE APPLICATION

    i. Understanding the codebase

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Analyze module for the hands-on enablement. [3 min]

    Before any modernization or maintenance effort can begin, engineers must first understand how a legacy application behaves. Much like Literate Coding allows developers to express change through natural language, Agentic AI enables developers to explore and understand unfamiliar codebases using conversational prompts.

    Tracing programs, copybooks, BMS maps and data stores by hand means reading across thousands of lines of COBOL. IBM Bob can analyze the same codebase in minutes and produce program documentation, architecture diagrams and change impact assessments from it.

    The effect is similar to working alongside a senior mainframe engineer: someone who can explain decades of accumulated business logic and say what breaks before you change it.

    In this module you will work with the CICS Banking Sample Application (CBSA), an enterprise-grade z/OS reference application. It simulates core retail banking operations: customer onboarding and account management, together with deposits, withdrawals and fund transfers.

    ii. Why this matters

    A deep understanding of the existing application reduces migration risk and improves modernization outcomes.

    Legacy-system analysis is particularly valuable when working with:

    • Large COBOL applications containing decades of business logic
    • Poorly documented systems where original developers are unavailable
    • Shared copybooks and BMS (Basic Mapping Support) maps where a single field change can ripple across many artifacts
    • Interdependent programs spread across presentation, business logic and data tiers
    • Modernization initiatives targeting Java, Python or cloud-native platforms
    TASK WITH: Manual Analysis WITH: IBM Bob Premium Package for Z
    Program documentation 1–2 days of analysis and writing Minutes of generation
    Architecture diagrams 2–3 days of manual creation Minutes of automatic generation
    Impact analysis Manual cross-referencing of every copybook and program Automatic, traceable blast-radius report
    Updates Difficult to maintain Instant regeneration

    iii. Explaining a program with Bob Workflows

    Begin with the built-in Explain code workflow to generate business-focused documentation for BANKDATA, the batch program that initializes CBSA's application data.

    1. Click the Explorer tab along the left edge of the Bob IDE.

      • The Bob PPZ L3 workspace from the Registration and setup chapter should already be open inside the Explorer tab.
      • Its src/base/ folder (or CBSA/src/base/) holds bms_src, cobol_copy, and cobol_src.
      CAN'T LOCATE THE DIRECTORY?

      If this is not the case:

      • Click Open Folder to expose the File Explorer view
      • Drill down into the Bob PPZ L3 folder and click Open

      ABOUT THE SCREENSHOTS IN THIS MODULE

      The screenshots were captured in a workspace folder named ppz-demo, with the three source folders sitting at its root. Your workspace is named Bob PPZ L3 and holds the same three folders under src/base/. The steps are otherwise identical.

    1. Near the top-right of the IBM Bob sidebar, click the Bob workflows button (the play icon) to open the workflow catalog. If a workspace picker appears first, select Run Workflow in Bob PPZ L3.

      WHAT ARE BOB WORKFLOWS?

      Workflows guide you through complex tasks step by step using built-in AI prompts. Instead of writing a prompt from scratch, you answer a few guided questions and Bob runs a multi-step analysis on your behalf.

    1. From the list of available workflows, locate Explain code and click Start.

    1. The Explain code workflow produces an explanation of the selected program. It analyzes the code with its copybook references and identifies the program logic, business rules and data usage.

      Under Program selection, click Browse files.

    1. In the file picker, navigate to src › base › cobol_src and select BANKDATA.cbl.

      Click Select File.

    1. Confirm that BANKDATA.cbl appears as the selected file, then click Continue with selection.

    1. Bob will ask which perspective the explanation should be written for.

      Select Business and click Confirm.

      EXPLANATION PERSPECTIVES

      The workflow offers three perspectives: Architect, Developer and Business. Each perspective produces a separate file with content tailored to that job role. You may re-run the workflow later to compare all three.

    1. Bob extracts the program's variables and generates the explanation.

      • When the workflow finishes, the Workflow results section shows where the explanation was saved.
      • Click the docs/explain/business_BANKDATA.md link to open it.

    1. Review the generated Business Summary & Analysis.

      Bob describes BANKDATA in business terms:

      • Its primary function: a batch data generation utility
      • The runtime parameters it accepts: START-KEY, END-KEY, STEP-KEY and RANDOM-SEED
      • The business rules it enforces, such as credit score assignment, account portfolio creation across product types and control record tracking for downstream reconciliation

      TRY IT WITH A PROMPT INSTEAD

      You can achieve a similar result without the workflow by typing /explain @src/base/cobol_src/BANKDATA.cbl in the chat. Bob will adapt the explanation to the currently active mode. With this approach Bob may not save the explanation automatically, so you may need to follow up with a prompt such as save the BANKDATA explanation.

    iv. Documenting the CBSA architecture with Z Architect mode

    The program explanation covers a single program in depth. Next you will have Bob document the architecture of the entire application: its programs, databases and major dependencies.

    1. Near the bottom of the Agentic Sidebar, press the Mode toggle to expand the list of modes and select Z Architect.

      SWITCHING BETWEEN DIFFERENT AGENTIC MODES

      The label assigned to the Mode toggle button will change to reflect the name of the mode that the Agentic Sidebar currently has active. For example, if in the Agent mode, the toggle button will read as Agent. For the sake of clarity, when instructing you to change the Agentic Mode type, this documentation will refer to this toggle button as the Mode toggle.

    1. With Z Architect mode active, copy and paste the following prompt into the Agentic Sidebar session window:

      Visually document the CBSA architecture in a .md file representing programs, databases, and major dependencies.

      With the prompt entered, hit Enter or press the Send button to the right of the chat interface.

      WHY Z ARCHITECT MODE?

      Z Architect mode specializes in creating architecture diagrams and analyzing application flows, which suits it to mapping inter-program relationships and producing structured documentation.

    1. Bob drafts a to-do list for the task: exploring the workspace, analyzing program dependencies and database access, and generating the documentation.

      Click Approve todo tools for task so Bob can update its progress without asking again.

      APPROVING TOOL REQUESTS

      Depending on your permission settings, Bob may also ask you to approve individual file reads or other tool calls as it works. Click Approve for each request as it appears.

    1. When all tasks are completed, Bob summarizes the highlights covered in the documentation, including:

      • System tiers: 29 COBOL programs split across presentation drivers, business logic services, an asynchronous credit bureau simulation and utilities
      • Persistence architecture: VSAM KSDS files (CUSTOMER and ABNDFILE) and Db2 tables (ACCOUNT, PROCTRAN and CONTROL)
      • End-to-end sequence flows such as customer onboarding, account creation and funds transfer
      • A copybook dependency matrix mapping the shared copybooks to the programs that use them

      Click the docs/cbsa_architecture.md link at the bottom of the response to open the full document.

      THE FILE NAME MAY DIFFER

      The workspace rules you created during setup tell Bob where to file its documents and how to name them. Bob may therefore save this document under a name that follows the [PREFIX]-[TYPE]-[description].md convention rather than the name shown in the screenshot. Follow the link in Bob's response.

    1. The Executive Summary & System Overview describes CBSA as a CICS application built on IBM CICS Transaction Server for z/OS, Db2 for z/OS and VSAM. It notes the clear separation between the presentation, business service and data layers.

      Scroll down to the High-Level Layered Architecture diagram to see how BNKMENU routes users to each screen driver.

    1. Continue scrolling to the Detailed Program Architecture & Catalog. Bob lists four things for every program: its transaction ID, its BMS mapset, its source file and the business services it calls. The result is a complete and navigable inventory of the application.

      OPTIONAL: GO FURTHER WITH ARCHITECTURE PROMPTS

      If you have token budget to spare, try these variations in Z Architect mode and compare the results:

      • Build an architecture diagram (in draw.io) illustrating the program dependencies of the CBSA application.
      • Create documentation with comprehensive call graphs of all programs in the workspace, organized by functional topics.

      Draw.io output produces an editable diagram that you can refine with follow-up prompts. One example is asking Bob to color-code the SELECT, INSERT, UPDATE and DELETE access on each table.

    v. Analyzing the impact of a field change

    A common maintenance question on the mainframe sounds simple: "What happens if I change this field?" A single copybook field can be shared by BMS maps, programs and runtime resources. In this section, Bob traces the full blast radius of shrinking one field before any code is touched.

    1. In the Explorer tab, expand the cobol_copy folder and open BANKMAP.cpy.

      Locate Line 14, which defines the company name input field:

      02  COMPANYI  PIC X(40).

    1. Highlight the entire line, then right-click and select IBM Bob › Add to Context to add the field to your active chat session.

    1. In the chat window, confirm the field has been added as context. It will appear as a tag reading BANKMAP.cpy:14.

      Before sending any instructions, press the Mode toggle and make sure Z Architect is selected.

    1. Within the Agentic Sidebar chat, type or paste the following prompt:

      What would be the impact of changing this field to 10? Generate Impact-Analysis.md

      Then hit Enter or press the Send button to execute the instruction.

    1. Bob recognizes the request and loads its impact-analysis skill. It then drafts a to-do list: read the copybook, identify every program that uses it, perform the dependency analysis and ask clarifying questions. Click Approve todo tools for task.

      APPROVING TOOL REQUESTS

      You may be asked to approve roughly 4–5 additional tool requests in sequence: skill requests, individual file reads and query requests. Click Approve for each one as it appears. Each approval allows Bob to complete the next step in tracing which artifacts reference COMPANYI.

    1. Before writing the report, Bob asks clarifying questions. For example, it may notice that the BMS source defines the field with a different length than the copybook, or that BANKMAP.cpy is referenced under a different member name.

      When prompted, select the option stating that the change is hypothetical/for analysis purposes and that Bob should document the full blast radius: the BMS source, the COBOL copybook and all downstream effects.

      RESPONSES MAY VARY

      Bob's questions are generated from its analysis, so the exact wording and number of questions may differ from the screenshot. Choose the option closest to a hypothetical, full blast-radius analysis. If Bob asks whether to include a Z Understand analysis, select the option to continue with the local analysis results only. Skip this step if you are not asked.

    1. When all tasks are completed, Bob saves the report to a date-stamped folder under bobz/impact-analysis/ and summarizes its Key Findings in the chat:

      • What must change: four artifacts

        • Both the input (COMPANYI) and output (COMPANYO) fields in BANKMAP.cpy
        • The DFHMDF LENGTH in bms_src/BNK1MAI.bms
        • The physical BMS map load module, reassembled and refreshed with CICS NEWCOPY
        • BNKMENU.cbl, recompiled and relinked

      • Most critical risk: if the copybook changes but the BMS source is not reassembled, the physical and symbolic maps fall out of sync by 30 bytes. Every subsequent field would be read or written at the wrong offset, causing silent data corruption or an ASRA abend

      • Inevitable business impact: the company name literal displayed on the main menu would be silently truncated, making the application title unrecognizable to users

      Click the report link in the response to open IMPACT-ANALYSIS.md.

    1. Review the Change Summary. Bob restates the change specification and explains why it cannot be made in isolation. It then captures the system context: the technologies involved, the entry point (BNKMENU.cbl under transaction OMEN) and the known dependencies.

    1. Scroll to the Scope Definition. Bob separates what is in scope from what is out of scope, and explains why.

      Notice that BNK1DDM.cpy also contains a field named COMPANYI, yet Bob correctly excludes it because it belongs to a different mapset. This is the kind of false positive that a plain text search would get wrong.

    1. Continue to the System Overview. The Components Analyzed table lists every affected artifact with its type, the change required and an impact level. It gives teams a ready-made checklist for planning the change.

      DIAGRAM NOT RENDERING?

      If the System Context Diagram shows a parse error instead of a diagram, Bob generated Mermaid syntax that the previewer could not read (often caused by special characters such as parentheses in node labels). Ask Bob to fix it with a follow-up prompt such as Fix the Mermaid syntax error in the System Context Diagram of IMPACT-ANALYSIS.md.

    vi. Key takeaways

    • Bob Workflows turn complex analysis tasks into guided, repeatable steps
    • Explanations can be tailored to Architect, Developer or Business audiences
    • Z Architect mode can document an entire application's programs, data stores and dependencies in minutes
    • Impact analysis traces the full blast radius of a change across copybooks, BMS maps, programs and runtime resources
    • Bob distinguishes true dependencies from look-alike fields, reducing false positives
    • Understanding change impact before touching code reduces risk and prevents production incidents
