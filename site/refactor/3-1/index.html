    MODULE 3 | REFACTOR

    MONOLITHIC COBOL REFACTORING AND SERVICE INTEGRATION

    i. From duplication to a shared service

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Refactor module for the hands-on enablement. [4 min]

    Each of the GenApp policy programs validates incoming requests in its own code. The same checks are written out separately in the programs that add, update and delete a policy — so a change to one rule has to be made in several places.

    In this module you will use IBM Bob to consolidate that logic. Bob will identify the validation rules and map everything that depends on them, move them into a single service program called LGPOLVAL, and update the original programs to call that service in place of their own checks.

    The programs you will work with across Module 3 | Refactor include:

    PROGRAM WHAT IT DOES
    LGAPDB01 Adds a policy
    LGUPDB01 Updates a policy
    LGDPDB01 Deletes a policy
    LGAPVS01 The VSAM program that LGAPDB01 calls when it adds a policy
    LGPOLVAL The new validation service, which does not yet exist. Bob creates it in section vi

    The module is deliberately structured. Sections iv and v are analysis only: Bob reads the code and produces documentation, and no source file is modified until the rules and their dependencies have been established. The refactoring itself begins in section vi.

    ii. Why this matters

    Refactoring a monolithic application is rarely as simple as cutting code out of one program and pasting it into another. The same rule is often written slightly differently in each place it appears, and the surrounding programs may depend on it in ways that were never documented.

    Agentic AI is well suited to this work because it:

    • Locates the rules in the source code and records where each one lives, down to the program and line number
    • Maps the dependencies before any code is moved, including calling programs, Db2 tables and shared copybooks
    • Produces documentation and test cases as part of the work, rather than leaving them for later
    • Keeps the human in the loop: every file change is presented for your review and approval before it is applied
    TASK WITH: Manual Analysis WITH: IBM Bob Premium Package for Z
    Business rules Read out of each program by hand Documented from the source, with program and line references
    Dependency mapping Cross-referencing programs, tables, and copybooks One mapping document with a dependency graph and diagrams
    Shared service Written by hand and documented afterwards Generated together with its documentation and test cases
    Integration Each calling program edited and checked separately Each edit proposed as a diff that you approve

    What the prompt asks What Bob does
    Map all programs that perform policy validation Identifies every program in which the request ID is inspected, the COMMAREA length is checked or a business rule is enforced. This extends beyond the three Db2 programs into the business-logic tier above them
    Check which programs call these validators Traces the CICS LINK chain from the screen programs at the top, through the business-logic programs, down to the Db2 and VSAM tiers

    Identify shared copybooks Lists each copybook, its purpose and every program that includes it

    Because this prompt is a follow-up within the same task, Bob builds on the findings of the first report rather than starting over. It also renders its diagrams as images and opens them in the editor as it works.

      The table contains two kinds of rule:

      • Rules that were explicitly coded, such as the request ID prefix check and the policy type checks for add, delete and update. Each existed in a slightly different form in each program (an inline IF in LGDPDB01 and an EVALUATE with a WHEN OTHER branch in the other two) and each is now a single check within the service
      • Rules that were only implied. None of the three programs verified that the customer number was non-zero or that a policy number had been supplied; each relied on Db2 to reject the request later. Bob implemented both as explicit checks that run before any Db2 work takes place

      Beneath the table, the LGPOLVAL COMMAREA Interface documents the contract defined in LGPOLVAL.cpy. A caller supplies an operation code, the request ID and the customer and policy numbers, and receives a result code and a readable reason in return:

      Field Picture Purpose

      VCA-REQUEST-ID X(6) Copied from the caller's CA-REQUEST-ID
      VCA-CUSTOMER-NUM 9(10) Copied from CA-CUSTOMER-NUM
      VCA-POLICY-NUM 9(10) Copied from CA-POLICY-NUM, zero for an add
      VCA-RESULT-CODE 9(2) 00 for pass, 10 to 50 for the check that failed
      VCA-RESULT-MSG X(40) A human-readable reason for the result

    1. The report closes with the Return Code Mapping and a diagram of the Architecture After Refactoring. The mapping is what keeps the change invisible to the programs upstream: each service result code is translated back into the CA-RETURN-CODE value that the caller has always returned, so the screen programs observe no difference.

      Service result Meaning Caller returns
      00 All checks passed Carries on with its Db2 work
      10 COMMAREA too short 98
      20 Unrecognised prefix or opcode 99
      30 Policy type not supported 99
      40 Customer number is zero 98
      50 Policy number required but zero 98

      The diagram illustrates the refactored chain. Each Db2 program links to LGPOLVAL with its own opcode; on a result of 00 the caller proceeds, and on any other result it sets CA-RETURN-CODE and returns without touching Db2.

      The explanation beneath the diagram accounts for the one program named in the prompt that was not wired to the service. Bob assigned LGAPVS01 an AV opcode in the service but did not add a LINK to it, because LGAPDB01 only reaches LGAPVS01 after validation has already passed; validating again in the VSAM tier would check the same request twice.

      Everything Bob has done in this module is a source change within your workspace. Before the change could be put to use, LGPOLVAL would need to be compiled and defined to CICS, and the refactored programs recompiled and tested. None of those steps are part of this lab.

    viii. Key takeaways

    • Bob documented the validation rules and mapped their dependencies before any code was changed
    • Each rule was traced back to the program and the lines it came from
    • The validation logic formerly repeated across the policy programs now resides in a single service, LGPOLVAL
    • The original programs reach the service through a CICS LINK and handle a failed call themselves
    • Every file change was presented as a diff for your approval before it was applied
    • Each section produced a report in the chat, so the refactoring is documented as well as implemented
    • A refactored program still has to be compiled, deployed and tested before the change is complete
