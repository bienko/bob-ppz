    MODULE 2 | BUILD

    IMPLEMENTING A NEW FEATURE IN COBOL

    i. From understanding to building

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Build module for the hands-on enablement. [3 min]

    In the previous module you used IBM Bob to understand the CICS Banking Sample Application: what each program does, how the application is layered, and what a single field change would cost you.

    This module puts that understanding to work. You will ask Bob to plan a new feature, review that plan as a human, and then have Bob write the COBOL to deliver it. Today, a bank teller connected to our hypothetical CICS application can only look up a customer by their numeric customer number. In the steps ahead, you will add the ability to search for a customer by email address.

    The pattern matters more than the feature itself. Plan feature changes first before you ultimately implement and build them. A plan is quick to read and costs little to change or throw away. Generated code that nobody planned costs far more to review and to undo.

    ii. Why this matters

    Adding a feature to a mainframe application is rarely a single-file edit. A new lookup path can touch the BMS screen and the screen driver, a new business service, and the COMMAREA contract between them, and the VSAM record layout itself.

    Agentic AI is valuable here because it:

    • Grounds the plan in the real codebase rather than in assumptions about how the application "probably" works
    • Surfaces gaps early, such as a field that the documentation claims exists but the copybook does not declare
    • Follows existing conventions by reusing the patterns already present in neighboring programs
    • Keeps a human in the loop, since every file change is proposed, reviewed and approved before it is implemented
    TASK WITH: Manual Analysis WITH: IBM Bob Premium Package for Z
    Design analysis Days of tracing programs and copybooks Minutes, grounded in the actual source
    Plan documentation Often skipped or written after the fact Produced first, as a reviewable artifact
    Code generation Hand-written, convention drift likely Follows the patterns in the existing suite
    Syntax verification Compile, read the errors and repeat Diagnostics plus a manual cross-check on request

    iii. Planning the change with Z Code mode

    1. Near the bottom of the Agentic Sidebar, press the Mode toggle to expand the list of modes and select Z Code.

      WHY Z CODE MODE?

      Z Code mode specializes in detailed analysis, documentation and generation of COBOL programs. Z Architect mode reasons about how the application fits together. Z Code mode works at the level of program structure: paragraphs, copybooks and CICS commands.

    1. Copy and paste the following prompt into the Agentic Sidebar session window:

      What is the plan to implement customer search by email? Create CBSA-plan-email-search.md

      With the prompt entered, hit Enter or press the Send button to the right of the chat interface.

      ASK FOR A PLAN FIRST

      This prompt asks for a plan only. It does not ask Bob to write the feature. Asking for a plan first gives you a document you can review, correct and share with your team before a single line of COBOL is generated.

    1. Bob drafts a to-do list covering the workspace exploration, the dependency analysis and the creation of the plan file. Click Approve todo tools for task.

      APPROVING TOOL REQUESTS

      If auto-approval is turned off, Bob will also ask permission for individual file reads and queries as it works. Click Approve for each request as it appears.

    1. When the task completes, Bob summarizes its key findings from the codebase and the structure of the plan it produced. Read this summary carefully before opening the file.

      Bob makes two key observations:

      • A critical gap: the architecture ER diagram describes an email field on the customer record, but CUSTOMER.cpy does not declare it. No email variable exists anywhere in the codebase, so adding that field is the prerequisite for everything else.
      • A VSAM constraint: the CUSTOMER file is a KSDS keyed only on sort code and customer number. With no alternate index on email, the search must be a full sequential browse using the same STARTBR / READNEXT / ENDBR pattern already used elsewhere in the suite.

      Bob also makes an explicit design decision: create a new service rather than extend the existing INQCUST program, so that the five existing callers of INQCUST are not broken.

      THIS IS THE REVIEW STEP

      A plan that contradicts what you know about your system is useful: the disagreement surfaced before any code was written. Read the design decision, the scope and the risks sections. If you disagree, say so in a follow-up prompt before any code is generated.

    iv. Implementing the plan

    1. Open CBSA-plan-email-search.md from the Explorer tab and review the full document. It holds the executive summary, a current-state analysis with a diagram of how customer lookup works today, the key programs table and the email field gap.

      THE FILE LOCATION MAY DIFFER

      The workspace rules you created during setup send Bob's documents to the docs/ folder. Bob may therefore have filed the plan there instead of at the workspace root. Follow the link in Bob's response.

      With the plan reviewed, send a follow-up prompt asking Bob to begin implementing it. For example:

      According to the implementation plan, update the CUSTOMER data structures
      • After copy and pasting the instruction above, hit Enter to execute the request.
      • Bob requests permission to use its COBOL code-generation skill.
      • Click Approve once to authorize it for this step, or Approve skill tools for task to authorize it for the remainder of the task.
      OPTIONAL: REFERENCING THE PLAN FILE DIRECTLY

      You can point Bob at the plan explicitly using the @ symbol in the chat bar, which inserts the correct path without you having to copy it manually:

      Use the @CBSA-plan-email-search.md file to implement the change

      Alternatively, right-click the file in the Explorer panel and select Copy Path, then paste the path into your prompt.

    1. Work through the plan step by step, approving each request as it appears. If auto-approve is turned off, Bob will prompt you before each individual change.

      As Bob applies the changes, the editor shows each modification as a diff: green lines indicate additions or new content, and red lines indicate removals or replaced content. The chat footer tracks how many files have changed, with Show all and Undo all controls available at any time.

    1. When the implementation completes, Bob summarizes the program it built. In this example it created cobol_src/INQEMAIL.cbl, named after the existing INQCUST convention and using the newly created SRCHEML.cpy copybook as its COMMAREA contract.

      The section structure table shows that Bob followed the conventions of the surrounding suite rather than inventing its own:

      • An entry-point section that validates the email is not blank
      • A browse section implementing the STARTBR / READNEXT loop with retry handling
      • A close-browse section called from every exit path
      • A populate-COMMAREA section
      • A CICS abend-handling section

    v. Verifying the generated code

    Generated code is a starting point. Bob can check its own work. In addition to your own review and checks, consider making a habit of asking Bob to review its own work, too, before treating the code as a deliverable.

    1. Within the Agentic Sidebar chat, copy and paste the following prompt:

      Verify the syntax of the INQEMAIL.cbl program

      Hit Enter or press the Send button to execute the instruction.

    1. Bob runs its diagnostic tooling and reports the results, then performs a manual cross-check of the artifacts it created.

      Three details in this output deserve attention:

      • The remaining warning is explained. Bob flags an unused-variable warning on the abend-handling section and assesses it as an expected false positive. That section is the target of a CICS HANDLE ABEND, so the CICS runtime activates it instead of a COBOL PERFORM. The same pattern appears in every program in the suite.
      • The cross-check is field by field. Bob confirms every field in the new COMMAREA copybook and in the updated customer record layout is correctly referenced, and verifies its CICS API usage against the existing INQCUST.cbl as a reference implementation.
      • A real defect was found and fixed. During the review Bob identified a string-continuation operator that is not valid IBM Enterprise COBOL syntax and corrected it.

      CLEAN DIAGNOSTICS ARE ONLY THE FIRST CHECK

      Clean diagnostics mean the program is syntactically sound and internally consistent. They do not guarantee that the feature behaves correctly. This requires further validation from a human-in-the-loop (you).

      The plan's testing section lists functional test cases, including edge cases, that still need to be executed against a running region before this change could be considered complete.

    vi. Key takeaways

    • Asking for a plan before asking for code produces a reviewable artifact and a better result
    • Bob grounds its plan in the real codebase, surfacing gaps that documentation alone would hide
    • Design decisions are made explicit, such as creating a new service rather than breaking existing callers
    • Generated COBOL follows the conventions already present in the surrounding programs
    • Every file change is proposed as a reviewable diff and requires your approval before it is committed
    • Asking Bob to verify its own work catches real defects and explains the warnings it chooses to leave in place
    • Syntax verification is a checkpoint on the way to functional testing, which is still required
